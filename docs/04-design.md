## 1. Architecture Overview

The voter-intent recording system consists of three logical layers:

```
┌─────────────────────────────────────────────────────────────┐
│                    CLIENT LAYER                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐           │
│  │  Voter App  │  │  Voter App  │  │  Voter App  │  ...     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘           │
└─────────┼─────────────────┼─────────────────┼────────────────┘
          │                 │                 │
          ▼                 ▼                 ▼
┌─────────────────────────────────────────────────────────────┐
│                    API LAYER                                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Ballot Recording Service                │   │
│  │  - Hash generation (SHA-256)                         │   │
│  │  - Retry logic with exponential backoff             │   │
│  │  - Quorum write confirmation                          │   │
│  └─────────────────────────────────────────────────────┘   │
```

## 2. Component Specifications

### 2.1 Ballot Record Schema

```json
{
  "_id": "ballot_<uuid>",
  "_rev": "<auto-generated>",
  "voter_id": "<hashed_identifier>",
  "contests": [
    {
      "contest_id": "president_2026",
      "selections": [
        {
          "candidate_id": "candidate_a",
          "rank": 1
        },
        {
          "candidate_id": "candidate_b",
          "rank": 2
        }
      ]
    }
  ],
  "intent_hash": "<sha256>",
  "timestamp_client": "<ISO8601>",
  "timestamp_server": "<ISO8601>",
  "signature": "<base64_signature>"
}
```

**Design Rationale:** The `intent_hash` is computed client-side before submission and verified server-side after storage to detect drift.

### 2.2 Shadow Document (Consistency Monitor)

```json
{
  "_id": "shadow_sequence",
  "_rev": "<auto-generated>",
  "global_sequence": 12345,
  "last_updated": "<ISO8601>",
  "node_id": "node_1"
}
```

**Purpose:** A monotonically increasing sequence number written with each ballot to detect gaps or duplicates.

### 2.3 CouchDB Configuration

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `chttpd__backlog` | 20000 | High connection limit |
| `couchdb__max_dbs_open` | 1000 | Handle many election databases |
| `revs_limit` | 100 | Conflict tracking window |
| `cluster__q` | 2 | Replication factor (n=3, w=2, r=2) |
| `cluster__n` | 3 | Total replica count |
| `delayed_commits` | `false` | Immediate durability for votes |

### 2.4 Consistency Level Configurations

```bash
# Eventual (default)
GET /ballots/ballot_id?r=1

# Sequential
GET /ballots/ballot_id?r=2&local_seq=false

# Strong
GET /ballots/ballot_id?r=3&w=3
```

## 3. Key Algorithms

### 3.1 Ballot Submission Flow

```
FUNCTION submit_ballot(ballot):
    # Step 1: Client-side intent preservation
    intent_hash = SHA256(ballot.contests + ballot.timestamp_client)
    ballot.intent_hash = intent_hash

    # Step 2: Retry with exponential backoff
    FOR attempt IN [1, 2, 3, 4, 5]:
        TRY:
            response = PUT /ballots/ballot_id (quorum write)
            BREAK
        EXCEPT IOException:
            WAIT (2^attempt * 100ms)

    # Step 3: Server-side verification
    stored_hash = GET /ballots/ballot_id.intent_hash
    IF stored_hash != intent_hash:
        LOG_CRITICAL("VOTER_INTENT_DRIFT", ballot_id)
        RETURN ERROR

    # Step 4: Confirmation
    RETURN SUCCESS
```

### 3.2 Voter-Intent Drift Detection

```
FUNCTION verify_intent(ballot_id):
    ballot = GET /ballots/ballot_id (strong quorum)
    expected_hash = SHA256(ballot.contests + ballot.timestamp_client)

    IF ballot.intent_hash != expected_hash:
        RETURN DRIFT_DETECTED
    ELSE:
        RETURN VERIFIED
```

### 3.3 Conflict Resolution Strategy

CouchDB stores conflicts as revision trees. Our resolution policy:

1. **Automatic (no conflict):** First-write-wins by `_rev` sequence
2. **Automatic (leaf conflict):** Shorter revision tree wins
3. **Manual (complex):** Flag for human review, block ballot certification

## 4. Failure Modes and Handling

| Failure Mode | Detection | Response |
|--------------|-----------|----------|
| Single node down | Health check timeout | Reroute traffic to healthy nodes |
| Network partition | Heartbeat failure | Switch to minority-read, majority-write |
| Split-brain | Version vector divergence | Halt writes, alert administrators |
| CouchDB crash | Process exit | Container restart via orchestrator |
| Disk full | Disk usage alert | Reject writes, graceful degradation |
| Hash mismatch | Intent verification fail | Block ballot, trigger audit |

## 8. Security Considerations (Summary)

- Voter identifiers hashed with SHA-256 (no plaintext PII stored)
- TLS 1.3 for all client-server and inter-node communication
- Ballot signatures verifiable via Ed25519 (optional enhancement)
- Rate limiting on ballot submission endpoint
- Audit log immutable (append-only CouchDB database)

**See `06-security-boundary.md` for detailed threat model and mitigations.**
